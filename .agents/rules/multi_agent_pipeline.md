# Протокол мультиагентной разработки (Multi-Agent Pipeline)

Данное правило обязательно для применения ко всем задачам написания, модификации или рефакторинга кода в проекте.

---

## 1. Концепция 4 ролей

Каждая задача по разработке кода должна последовательно проходить 2 итеративных цикла с участием 4 специализированных ролей агента:

```text
[Фаза 1: Архитектура]
  Агент 1 (Архитектор) <──── Итерации правок ────> Агент 2 (Критик архитектуры)
                                                           │
                                                           ▼ [ARCH_APPROVED]
[Фаза 2: Реализация]
  Агент 3 (Разработчик) <──── Итерации правок ───> Агент 4 (Code Reviewer / QA)
                                                           │
                                                           ▼ [CODE_APPROVED]
                                                Тесты (npm test) -> Git push -> Actions
```

---

## 2. Фаза 1: Архитектурное проектирование

### Роль 1: Архитектор (System Architect)
* Анализирует задачу, контекст проекта и существующие модули из `.ai/`.
* Формирует проект решения:
  1. Выбор места размещения файлов (сервер/клиент/shared).
  2. Экспорт типов (`export type`) и контракты сетевых событий (`RemoteEvent` / `RemoteFunction`).
  3. Границы ответственности модулей и потоки данных.
* Передает спецификацию Агенту 2.

### Роль 2: Критик архитектуры (Architecture Reviewer / Skeptic)
* Проводит стресс-тест архитектуры на типичные для Roblox проблемы:
  1. **Сетевая безопасность**: Может ли эксплойтер подделать аргументы? Валидируются ли типы и рейты?
  2. **Утечки памяти / Жизненный цикл**: Очищаются ли соединения (`RBXScriptConnection`) и детали (`Debris`)?
  3. **Согласованность данных**: Возможны ли состояния гонки (race conditions) при выходе игрока или задержке сети?
  4. **Совместимость**: Не ломает ли решение существующую геометрию или экономику?
* **Цикл обратной связи**: Если найдены риски — формулирует замечания. Агент 1 перерабатывает архитектуру, пока Агент 2 не выдаст вердикт `[ARCH_APPROVED]`.

---

## 3. Фаза 2: Реализация и проверка качества

### Роль 3: Разработчик кода (Code Implementer)
* Пишет реализацию строго по одобренной архитектуре.
* Требования к коду:
  1. Строгая типизация Luau: первая строка всегда `--!strict`.
  2. Соответствие правилам Selene и форматированию StyLua.
  3. Обязательное написание юнит-тестов в каталоге `tests/` для каждого нового модуля/механики.
* Передает код Агенту 4.

### Роль 4: Код-ревьюер и QA (Code Reviewer & QA)
* Проверяет качество реализации:
  1. Корректность типизации и отсутствие скрытых приведений типов.
  2. Оборачивание внешних вызовов (DataStore, Marketplace) в `pcall`.
  3. Полнота покрытия тестами штатных и краевых сценариев.
  4. Запуск раннера тестов (`npm test`).
* **Цикл обратной связи**: Если тесты не проходят или есть дефекты реализации — возвращает конкретные правки Агенту 3. Итерации продолжаются до получения вердикта `[CODE_APPROVED]`.

---

## 4. Финализация и соблюдение регламента проекта
После получения `[CODE_APPROVED]`:
1. Запустить локальный прогон всех тестов (`npm test`) и убедиться в 100% успехе.
2. Обновить документацию проекта в папке `.ai/` (`ARCHITECTURE.md` / `PROJECT_OVERVIEW.md`).
3. Закоммитить изменения и отправить пуш в ветку `main`.
4. Дождаться успешного завершения пайплайна GitHub Actions через GitHub API (`gh run watch` / API).
