# Протокол мультиагентной разработки и ревью кода (Multi-Agent Pipeline & Multi-Lens Review)

Данное правило обязательно для применения ко всем задачам:
1. Написания, модификации или рефакторинга кода в проекте.
2. Автономного ревью кода существующих файлов или PR по запросу пользователя.

---

## 1. Схема конвейера

```text
[Фаза 1: Архитектурное проектирование]
  Агент 1 (Архитектор) <──── Итерации правок ────> Агент 2 (Критик архитектуры)
                                                           │
                                                           ▼ [ARCH_APPROVED]
[Фаза 2: Реализация и Коллегия Ревью (Multi-Lens Audit Board)]
  Агент 3 (Разработчик) ◄─────────────────────────┐
       │                                          │ Итерации правок
       ▼                                          │ при P0/P1
  ┌───────────────────────────────────────────┐   │
  │    Коллегия Ревью (Multi-Lens Review)     │   │
  │  • 🛡️ Security & Exploit Auditor          │   │
  │  • ⚡ Performance & Memory Hunter          │   │
  │  • 💣 Chaos & Edge-Case Engineer          │   │
  │  • ⚖️ Lead Arbiter (Сводный вердикт)      │───┘
  └───────────────────────────────────────────┘
                       │
                       ▼ [CODE_APPROVED]
         Тесты (npm test) -> Git push -> Actions
```

---

## 2. Фаза 1: Архитектурное проектирование

### Роль 1: Архитектор (System Architect)
* Анализирует задачу, контекст проекта и существующие модули из `.ai/`.
* Формирует спецификацию:
  1. Размещение файлов (сервер/клиент/shared).
  2. Экспорт типов (`export type`) и сетевой контракт (`RemoteEvent` / `RemoteFunction`).
  3. Границы ответственности модулей и потоки данных.
* Передает спецификацию Агенту 2.

### Роль 2: Критик архитектуры (Architecture Reviewer / Skeptic)
* Стресс-тест архитектуры на уровне концепции:
  1. Защита сетевого взаимодействия (античит/подделка пакетов).
  2. Риски состояний гонки (race conditions) и утечек памяти.
  3. Совместимость с экономикой и пространственной геометрией баз.
* **Цикл обратной связи**: Агент 1 перерабатывает схему до вердикта `[ARCH_APPROVED]`.

---

## 3. Фаза 2: Реализация и Коллегия Ревью (Multi-Lens Audit Board)

### Роль 3: Разработчик кода (Code Implementer)
* Пишет реализацию строго по одобренной архитектуре.
* Требования к коду:
  1. Строгая типизация Luau: первая строка `--!strict`.
  2. Правила линтинга Selene и форматирования StyLua.
  3. Обязательное создание юнит-тестов в каталоге `tests/` на каждый новый модуль.
* Передает готовый код Коллегии Ревью.

### Роль 4: Коллегия Ревью кода (Multi-Lens Audit Board)
Ревью кода проводится параллельно через 4 специализированные линзы:

1. 🛡️ **Security & Exploit Auditor (Безопасность и анти-эксплойт)**:
   * Проверка всех `OnServerEvent` на валидацию типов аргументов, защиту от `NaN`, `math.huge`, отрицательных сумм.
   * Проверка прав доступа (не может ли чужой игрок вызвать чужую кнопку или чит).
   * Ограничение частоты вызовов (Rate Limiting) от сетевого спама.

2. ⚡ **Performance & Memory Hunter (Производительность и память)**:
   * Проверка отписки от событий (`RBXScriptConnection:Disconnect()`).
   * Очистка временных инстансов в `workspace` через `Debris:AddItem` или `:Destroy()`.
   * Отсутствие аллокаций тяжелых таблиц в циклах `Heartbeat`/`RenderStepped`.
   * Оптимизация пространственных запросов (`OverlapParams`).

3. 💣 **Chaos & Edge-Case Engineer (Краевые случаи и устойчивость к сбоям)**:
   * Что будет, если игрок отключился или умер в момент выполнения действия?
   * Что будет при сбое сети или ошибке `DataStoreService`? (Обязателен ли `pcall`?).
   * Корректность работы при нулевых или граничных балансах.

4. ⚖️ **Lead Arbiter (Главный арбитр & QA)**:
   * Сводит замечания всех 3 экспертов и классифицирует по приоритетам:
     * **P0 (Критический)**: дыра в безопасности, краш сервера, потеря данных. Блокирует приемку.
     * **P1 (Важный)**: утечка памяти, некорректная логика, отсутствие тестов. Блокирует приемку.
     * **P2 (Рекомендация)**: код-стайл, улучшение читаемости. Не блокирует.
   * Запускает локальный тестовый раннер (`npm test`).
   * При наличии замечаний P0/P1 возвращает Агенту 3 конкретный список правок. Цикл повторяется до получения вердикта `[CODE_APPROVED]`.

---

## 4. Автономный режим ревью (Standalone Review Mode)

Когда пользователь запрашивает:  
*«Сделай ревью кода»*, *«Проверь файл X на баги»*, *«Проведи аудит безопасности»* —  
автоматически активируется **Коллегия Ревью (Multi-Lens Audit Board)**:
* Отчет формируется строго по 4 секциям (🛡️ Безопасность, ⚡ Производительность, 💣 Сбои, ⚖️ Итог Арбитра с P0/P1/P2 и готовыми diff-патчами).

---

## 5. Финализация и соблюдение регламента проекта
После получения `[CODE_APPROVED]`:
1. Запустить локальный прогон всех тестов (`npm test`) — 100% успех.
2. Обновить документацию проекта в папке `.ai/`.
3. Закоммитить изменения и отправить пуш в ветку `main`.
4. Дождаться успешного завершения пайплайна GitHub Actions через GitHub API (`gh run watch`).
